1. Purpose & Scope

This standard defines the minimum technical, scientific, interaction, UI/UX, 3D, WebGL performance, testing, progress-tracking and delivery requirements for outsourced BEDO Unity virtual laboratory projects.

Core principle: A visually correct demonstration is not sufficient for acceptance. A delivery is accepted only when all applicable mandatory gates pass, all required evidence is supplied, and no open Critical or Major defects remain.

Applies to

  • New Unity virtual laboratories.
  • Major upgrades to existing laboratories.
  • Windows desktop and WebGL delivery.
  • Projects integrated with BEDO progress/LMS reporting.

Rule classes

Mandatory failure blocks the gate.

Conditional mandatory when the referenced feature is in scope.

Advisory improvement note; does not block by itself.

2. Acceptance Model & Defect Severity

SeverityTypical ExamplesAcceptance Effect
CriticalWrong mandatory scientific result, unrecoverable crash, corrupted experiment state, project cannot build/run.Blocks acceptance immediately.
MajorCore experiment step impossible, reset broken, Guided/Free inconsistency, severe performance degradation, major UI path inaccessible.Blocks acceptance.
MinorLocalized UI/content issue with no scientific or workflow impact.May be accepted only if BEDO explicitly records it on a punch list.
Cosmetic / AdvisoryPure polish with no functional effect.Does not block unless the project brief makes it mandatory.

Milestone decision: ACCEPTED only when every applicable mandatory gate is PASS, all required evidence is supplied, and there are no open Critical or Major defects. Otherwise: RETURNED FOR CORRECTION.

3. Gate A — Unity Architecture, Prefabs & Project Structure

RuleRequirementPASS WhenRequired EvidenceApplicability
A-01 Approved Unity Version Use Unity 6000.0.60f1 unless BEDO approves a written exception. Package/plugin versions shall be pinned and shall not be upgraded/downgraded without approval. Project opens, builds and runs on the approved version with no forced migration. ProjectVersion.txt, package manifest, build log. Mandatory
A-02 SOAP State Architecture Use SOAP references for tunable gameplay/configuration values and shared experiment state. Avoid unmanaged duplicated raw state across unrelated components. Critical experiment values have one identifiable authoritative source of truth. State map, representative SOAP assets, source review. Mandatory
A-03 Prefab Integrity Reusable laboratory equipment shall remain connected to its source Prefab. Unpack Completely is prohibited for reusable content unless BEDO approves a documented exception. Repeated content exists as prefab instances with intentional overrides/variants instead of duplicated scene hierarchies. Prefab audit, scene inspection, hierarchy screenshots. Mandatory
A-04 Nested Prefabs & Variants Use Nested Prefabs and Prefab Variants when reusable structures need controlled differences. Structural differences are implemented without copy-paste duplication. Prefab relationship review. Mandatory
A-05 Scene Hierarchy Discipline Hierarchy must be readable, grouped by responsibility, and free of unexplained duplicate object trees. Reusable equipment must not be manually duplicated as independent object copies. A reviewer can locate experiments, reusable systems, UI, cameras, lighting and equipment without tracing arbitrary object names. Hierarchy review. Mandatory
A-06 Asset Folder Organization Production assets shall be organized at minimum into clear folders such as Models, Materials, Textures, Prefabs and Scenes. Assets can be traced and maintained without searching through mixed/unstructured folders. Project tree screenshot. Mandatory
A-07 No Hidden Global Coupling Do not rely on undocumented globals, static state, scene-name side effects or local developer-machine paths for core behavior. Project behavior is reproducible from a clean checkout and scene ownership is explicit. Architecture note, clean-build test. Mandatory

4. Gate B — Scientific & Simulation Correctness

RuleRequirementPASS WhenEvidenceApplicability
B-01 Approved Scientific Model Equations, relationships, assumptions, units and sign conventions shall match the approved project specification. No unapproved substitutions, clamps or simplified logic affect mandatory reference cases. Reference-case table, formula/config trace, test results. Mandatory
B-02 Cross-View Consistency 3D equipment, software monitor, gauges, labels and graphs shall represent the same authoritative scientific state, allowing only approved display rounding. No view displays a conflicting value for the same state. Cross-view screenshots/tests. Mandatory
B-03 Guided / Free Numerical Parity Guided Mode may control sequence and access, but shall not own a separate scientific truth unless explicitly specified. Identical accepted physical inputs produce the same scientific result in Guided and Free modes. Parity test. Conditional
B-04 Valid Power / Wiring Logic Power states, lamps, displays, instruments, wires and warnings shall follow the approved physical/electrical logic. No device appears powered when disconnected; valid wiring does not trigger incorrect warnings; invalid wiring cannot produce a valid result. Positive/negative wiring tests. Mandatory
B-05 Boundary & Special Cases Zero values, maxima, minimums, mode boundaries, disconnected states and required special cases shall be tested. All approved boundary scenarios behave correctly. Boundary test suite. Mandatory
B-06 Reset Removes Prior Influence Reset/restart shall return the experiment to the approved initial state with no hidden scientific leftovers. A rerun after reset matches a fresh run for the same inputs. Reset/repeat test. Mandatory

5. Gate C — Gameplay, Guided Mode & Free Mode

RuleRequirementPASS WhenEvidenceApplicability
C-01 Single Interaction Owner Each control or interactive object shall have one clear owner. Double bindings and competing handlers are prohibited. One user action creates one intended state transition. Interaction test. Mandatory
C-02 Guided Mode Step Control Guided Mode shall expose/highlight only the interactions required by the current step unless specified otherwise. Unrequired controls cannot skip/completely bypass the intended procedure; required controls are discoverable. Guided E2E test. Conditional
C-03 Free Mode Independence Free Mode shall support approved physical interactions without hidden dependency on Guided Mode state. Approved interactions work in valid order without requiring guided-step state. Free-mode E2E test. Conditional
C-04 Mode Switching Switching between Guided and Free shall not silently alter scientific inputs or create impossible states. State is preserved or reset only according to the approved rule. Mode-switch test. Conditional
C-05 Camera/View Consistency Camera transitions shall support the task without resetting values, duplicating actions or making required controls inaccessible. View changes preserve valid experiment state. Camera E2E test. Mandatory
C-06 Rapid Input Safety Fast dragging, repeated clicking or slider motion shall not skip mandatory checkpoints or corrupt state. Stress interaction follows the intended procedure and remains recoverable. Rapid-input test. Conditional
C-07 Reset / Restart Reset shall be complete, repeatable and idempotent. Repeated reset/restart produces the approved initial state every time. Reset ×20 report. Mandatory

6. Gate D — UI, UX, Graphs & Camera Presentation

RuleRequirementPASS WhenEvidenceApplicability
D-01 Approved UI System Use the approved BEDO UI design/reference assets. Do not invent a local visual language where approved patterns already exist. Panels, buttons, monitor, warnings, toolboxes and experiment navigation match approved references. UI comparison review. Mandatory
D-02 Standard Control States Normal, hover, pressed, selected, disabled, focus and error states shall be visually distinguishable where applicable. Control behavior matches the approved pattern. UI state checklist. Mandatory
D-03 Resolution & Scaling Reference resolution is 1600×900, 16:9. Minimum supported presets: 1280×720, 1600×900, 1920×1080, 2560×1440, 3840×2160. Use Canvas Scaler → Scale With Screen Size, reference 1600×900, Match 0.5. No clipping, overlap or inaccessible controls at approved target sizes. Resolution screenshot matrix. Mandatory
D-04 WebGL Browser Zoom UI must remain usable and visually correct at browser zoom 90–125% with no text clipping. All mandatory screens remain readable and operable across the approved zoom range. Browser screenshot matrix. Mandatory
D-05 Graph / Table Behavior Graphs, tables, scroll areas, numeric rows and labels must remain aligned, readable and synchronized with authoritative values. No duplicated rows, independent column drift, broken scrolling, overlapping text or conflicting values. Graph/table functional test. Conditional
D-06 Warning Quality Learner-facing warnings shall explain the required corrective action and must not display raw developer errors. Warnings are correct, actionable and appear only in the proper state. Negative-path UI tests. Mandatory
D-07 Visual Regression Approved screenshots shall be stored for key experiment/UI states and compared against future builds. Unexplained differences are resolved before acceptance. Visual regression report. Mandatory

7. Gate E — 3D Assets & Scene Optimization

RuleRequirementPASS WhenEvidenceApplicability
E-01 FBX & Units Models shall be exported in FBX format with unit scale consistently set to meters. Scale is consistent and scientific/render coordinates are traceable. Import settings and asset audit. Mandatory
E-02 Spatial Consistency Approved lab coordinates and trainer placement must be preserved. Models align to approved scene coordinates without corrective arbitrary offsets. Scene inspection. Mandatory
E-03 Pivot Setup Pivots shall be correctly prepared for knobs, gauge handles, fluids, buttons, valves and other interactive elements. Interactive movement occurs around the intended physical pivot. Interaction inspection. Mandatory
E-04 Normalized Transforms Object scales shall be normalized/reset before export where required. Imported object transforms are clean and predictable. Transform audit. Mandatory
E-05 Geometry & Texture Optimization Topology and texture resolution shall be appropriate to WebGL performance needs. Avoid unused large assets and uncontrolled duplication. Scene/build statistics stay inside the approved performance budget. Asset statistics report. Mandatory
E-06 Lighting Restrictions No real-time lighting, reflection probes or shadows unless specifically approved. Prefer baked/low-cost presentation suitable for web deployment. Web build meets visual and performance targets without prohibited lighting cost. Scene settings review. Mandatory

8. Gate F — WebGL, Performance, Stability & Resource Management

Mandatory delivery: Every applicable laboratory shall provide a working WebGL build in addition to the Windows build. Performance acceptance is measured on agreed reference devices, not only on the developer workstation.
RuleRequirementPASS WhenEvidenceApplicability
F-01 Reference Environment Every performance run shall identify device, CPU/GPU/RAM, OS, browser, viewport and quality preset. Results are reproducible on the agreed environment. Acceptance sheet. Mandatory
F-02 Windows FPS — Baseline Device Windows x86_64 IL2CPP: average ≥30 FPS; 99th-percentile frame time ≤45 ms; no single hitch >200 ms. 10-minute run meets all criteria. Profiler/performance capture. Mandatory
F-03 Windows FPS — High-End QA Device Target ≥120 FPS; capping at 120 is acceptable. Measured run meets target on the agreed high-end QA device. Performance capture. Mandatory
F-04 WebGL FPS — Baseline Device Average ≥25 FPS. 10-minute run in the most demanding typical scene meets target. Browser performance capture. Mandatory
F-05 WebGL FPS — High-End QA Device Target ≥60 FPS (browser vsync). Measured run meets target. Browser performance capture. Mandatory
F-06 Measurement Protocol Measure over a continuous 10-minute session in the most demanding typical scene. Baseline Device shall be plugged in and set to High Performance power mode. Run is continuous and representative of normal learner interaction. Recorded test protocol. Mandatory
F-07 WebGL Build Settings Use WebGL 2.0, Brotli compression, Data Caching on, Exceptions disabled, and controlled initial memory (starting 512–768 MB; changes require approval). Acceptance build uses approved settings and has no OOM failures in normal flows. Player settings screenshots/build config. Mandatory
F-08 Low Quality Preset For baseline hardware: Shadows Off or Hard Low; Texture Max Size ≤1024; Anisotropic Off; Post-processing Off; optional Resolution Scale 0.8–1.0. Preset is selectable/usable as specified and performance target is met. Quality settings review. Mandatory
F-09 Runtime Allocation & GC Discipline Avoid large runtime allocations and long GC spikes. Reuse objects/resources where practical. No repeated stutter caused by avoidable allocations during normal use. Profiler capture. Mandatory
F-10 Scene / Mode Transition Experiment switching, Guided↔Free, reset and reload must not produce excessive black screens, freezes or partially initialized interaction. Transitions reach Ready state within the approved project-specific budget and remain responsive. Transition timing report. Mandatory
F-11 Performance Regression After the first approved release, major load-time, scene-size, frame-time or FPS regression requires explanation and approval. New build stays within the approved baseline or has a documented exception. Release comparison report. Conditional

9. Gate G — Testing, Regression & QA

RuleRequirementPASS WhenEvidenceApplicability
G-01 Scientific Reference Cases Each experiment shall define approved inputs/states and expected outputs/behaviors. All mandatory cases pass within approved tolerance. Reference-case table/report. Mandatory
G-02 State & Interaction Tests Critical state transitions, invalid operations, reset and mode switching shall be tested. Mandatory interaction/state scenarios pass. Test report. Mandatory
G-03 Bug Regression Rule Every fixed Critical or Major defect that can reasonably recur shall receive a documented regression test or repeatable validation case. Regression check exists and passes before defect closure. Defect record + regression evidence. Mandatory
G-04 No Regression of Approved Features A new build must not break a feature or experiment state previously approved without an approved change request. Regression checklist passes across previously approved flows. Build-to-build comparison. Mandatory
G-05 No Runtime Error Spam Normal approved flows shall not generate repeated exceptions, error logs or development debug spam in the acceptance build. Console/log review is clean for mandatory flows. Log capture. Mandatory
G-06 Reset ×20 Stability Complete flow/reset cycle shall be repeatable without accumulating broken state, duplicate listeners or resource leaks. Twenty consecutive reset/restart cycles complete without degradation. Reset ×20 report. Mandatory

10. Gate H — Progress Tracking, Questions & LMS Integration

Scope: The initial BEDO progress implementation is intentionally simple: track required experiment steps, record question outcomes, and report lifecycle events. Progress, completion and grading remain separate concepts.

10.1 Required-Step Progress

Progress % = 100 × (Distinct Completed Required Tracked Steps / Total Required Tracked Steps)
  • tracked = false items are navigation/non-progress and do not count.
  • Each required tracked step contributes at most once at a time within one attempt.
  • StepRetried removes the previous contribution until the step is completed again.
  • Progress is calculated per experimentAttemptId; separate attempts shall not be merged.

10.2 Project Manifest

Every LMS-integrated release shall provide stable project data including:

FieldRequirement
projectIdStable project identity.
projectVersionExact published simulation build version.
assessmentVersionLearning/assessment definition version.
experimentIdStable experiment identity.
stepNumberStable numeric catalog number; do not renumber by visit order.
trackedWhether the step emits/counts progress.
requiredForCompletionWhether the tracked step contributes to required progress.
questionIdStable question identity.
questionTypeCurrently MultipleChoice or TrueFalse.

10.3 Minimum Lifecycle Events

The reusable BEDO reporter shall support the approved schema 2.1 event semantics including:

SessionStarted · SessionCompleted · ExperimentStarted · ExperimentCompleted · ExperimentAborted · StepStarted · StepCompleted · StepFailed · StepRetried · QuestionShown · QuestionAnswered · QuestionCorrect · QuestionIncorrect

10.4 Questions — Learner Feedback Policy

RuleRequirementPASS WhenEvidenceApplicability
H-01 Hide Correct/Incorrect Result After answer submission, the learner shall not be shown whether the answer was correct or incorrect unless the project specification explicitly requires feedback. No green/red correctness indicator shall be shown by default. Question submission proceeds without revealing correctness to the learner. UI review + E2E question test. Mandatory
H-02 Record Answer Outcome Internally Each answer submission shall record Question ID, selected answer, attempt number, and corresponding Correct/Incorrect result. Every submitted answer has exactly one recorded result event. Event log / LMS test. Mandatory
H-03 Progress Sheet Question Summary The learner progress record shall maintain at minimum: Answered Questions, Correct Answers, Incorrect Answers per experiment attempt. Summary counts match the underlying recorded submissions/results. Progress sheet / LMS report. Mandatory
H-04 Retry Attempts Each new answer submission to the same question increments attempt starting at 1. Previous attempts remain recorded. Wrong → retry → correct creates two distinct submissions/results with attempt numbers 1 and 2. Question retry test. Mandatory
H-05 Progress ≠ Completion ≠ Grade Step progress percentage, ExperimentCompleted lifecycle state, and numeric/pass-fail grading shall remain separate. ExperimentCompleted shall not manufacture missing step/question evidence or automatically award 100%/pass. Each concept is stored and reported independently. State/report review. Mandatory
H-06 No LMS Dependency for Scientific Truth Scientific solver and learner interaction shall remain functional if LMS/network reporting is unavailable. Loss of reporting transport does not change experiment calculations or physical state. Offline/transport-failure test. Mandatory

11. Gate I — Delivery, Versioning & Documentation

RuleRequirementPASS WhenEvidenceApplicability
I-01 Complete Unity Project BEDO shall receive the complete project source and all project-owned assets needed to build. Independent reviewer can open and build the project. Repository/project package access. Mandatory
I-02 Windows + WebGL Builds Submit acceptance Windows and WebGL builds mapped to the exact project version/revision. Both required builds run successfully on the agreed environments. Build packages + version identity. Mandatory
I-03 Release Identity Every accepted build shall have a unique projectVersion. Visual/technical fixes still require a new project version. Reviewer can identify exactly which source/build produced the delivery. Release note / tag / build ID. Mandatory
I-04 Assessment Versioning If step meanings/order, required items, questions, answer meaning, correct answers or grading rules change, assessmentVersion shall change. Assessment-equivalent fixes preserve assessment version; learning-definition changes do not. Version comparison note. Conditional
I-05 Known Issues All known defects and limitations shall be disclosed. Known-issues list matches observed build state. Release notes. Mandatory
I-06 Validation Package Delivery shall include current scientific validation, QA/regression, visual comparison, performance and progress/LMS test evidence where applicable. All reports correspond to the delivered build. Evidence package. Mandatory
I-07 Progress/LMS Package When progress integration is in scope, deliver projectId, projectVersion, assessmentVersion, manifest, question catalog, completion definition and contract-test results. Runtime manifest matches the approved registered project definition. Manifest + LMS contract test report. Conditional
